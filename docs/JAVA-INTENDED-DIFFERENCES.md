# Java 코어가 TypeScript 코어와 일부러 다르게 하는 것

`docs/JAVA-BACKEND-MIGRATION.md` 5장의 "의도된 차이" 표입니다. Java 코어(`attest/apps/core-java`)의 응답은 TypeScript 코어(`attest/apps/core`)와 같아야 하고, 여기에 적힌 것만 다릅니다. 여기에 없는 차이는 결함입니다.

대조 도구(`apps/core-java/parity/run.mjs`)가 실제로 만나는 차이는 `apps/core-java/parity/expected.json`에 이 문서의 번호와 함께 적습니다.

- **상태:** 5단계 1부 기준 (2026-11-18: Attest API, 배치 워커, 인스크립션, 콘솔 API, 샌드박스 자료 4개와 정산 증빙 2개, 송금 레일이 콘솔에 등록하는 경로 3개, 준비금 증명 5개. 2026-11-19: 송금 레일 1부 — 접수와, 파트너를 부르지 않는 경로 11개. 접수 뒤의 파이프라인과 나머지 경로 3개는 2부). 단계가 끝날 때마다 갱신합니다.

## 서버가 먼저 거절하는 요청

경로에 무엇이 들어 있든(잘못된 `%` 이스케이프, `%00`, 루트 위로 올라가는 `..`, 역슬래시, `"<>[]^{|}` 같은 문자) Java 코어는 요청 줄의 경로를 그대로 받아 TypeScript 코어와 같은 규칙으로 읽습니다(`http/RawTargetAdapter`, `http/RequestTarget`). 대조 230건에서 차이가 없습니다.

HTTP 문법 자체가 깨진 요청은 서버가 라우터에 넘기기 전에 닫습니다. 이 층은 두 구현이 서로 다른 제품(Node, Tomcat)이라 문장까지 맞추지 않습니다.

| 요청 | TypeScript(Node) | Java(Tomcat) |
|---|---|---|
| 요청 줄과 헤더가 16 KiB를 넘음 | 431 | 400 |
| 요청 대상에 제어 문자, 공백, ASCII가 아닌 바이트 | Node가 정한 대로 | 400 |
| 호스트 이름이 들어간 요청 대상(`//host/path`)의 국제화 도메인 검사 | URL 표준대로 | 검사하지 않음(ASCII 이름과 IPv4는 같음) |

## 인스크립션의 한계

TypeScript 코어에서 그대로 가져온 성질이고, 고치지 않았습니다. 이 경로의 약속은 "공개되지 않은 문서를 담은 기록은 없다"이고, 그래서 **전송이 먼저, 기록이 나중**입니다(리빌 트랜잭션이 문서를 담고 있으므로 전송 전에 적어 두지 않습니다). 배치 앵커의 "전송 전 기록"(S-10)은 여기에 쓰지 않습니다. 아래는 코드의 순서에서 나오는 것이고, 일부러 일으켜 보지는 않았습니다(일으키려면 코인이 듭니다).

- **전송과 기록 사이에 멈추면** 인스크립션은 체인에 있고 서비스는 그것을 모릅니다(행이 없음). 같은 문서를 다시 보내면 중복으로 막히지 않고 새 인스크립션이 만들어집니다. Java 코어는 전송 직후 로그 한 줄을 남깁니다(S-14).
- **노드가 리빌을 받고도 답하지 못하면**(타임아웃) 요청은 500으로 끝나고 기록이 없습니다. 위와 같은 상태입니다.
- **커밋이 나간 뒤 리빌이 거절되면** 커밋 출력(1,000 sat + 리빌 수수료)은 그 인스크립션에 쓰려고 뽑은 키로만 쓸 수 있고, 그 키는 버려집니다. 회수할 수 없습니다. 크기와 `Content-Type` 검사는 지갑에 묻기 전에 합니다(D-09).
- **같은 문서를 동시에 두 번 보내면** 중복 검사는 전송 전에, 유일 키는 기록할 때 걸리므로 두 인스크립션이 모두 전송되고 하나만 기록됩니다. 늦은 쪽은 409를 받습니다(D-05).
- **워커가 꺼진 인스턴스만 있으면**(`WORKER_TICK_MS=0`) 확정 갱신이 없어 `submitted`에 머뭅니다. regtest의 블록(S-12)도 워커가 만듭니다.
