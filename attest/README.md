# StoneHash Attest

Independently verifiable digital evidence: hash a record, commit it to Bitcoin,
and hand the holder a file that anyone can check without contacting us.

```
attest/
├── packages/attest-verify/   Independent verifier · zero dependencies · Node + browser
├── packages/attest-rules/    Settlement rules engine · policies as data · six axes · P-256 issuer signatures
├── packages/attest-evidence/ Evidence archive assembly · deterministic ZIP + report
├── apps/core/                Attest Core · single process · issue → batch → anchor → bundle
├── apps/playground/          Browser verifier · no bundler, no framework, no backend
├── apps/docs/                Developer Hub · API reference, spec, test vectors
├── apps/console/             Sandbox Console · self-serve accounts · T2
├── fixtures/                 Published wire contract + conformance bundles
└── deploy/                   Portable run / regtest / smoke / pm2 scripts
```

## Design constraints this repository is built around

**One process, not a service mesh.** Issue, batch, anchor and export are one
workflow over one database, so they live in one deployable. The batcher is a
timer inside the API process. There is no broker, no gateway and no per-service
deployment unit.

**Zero runtime dependencies.** `node --test` is the test runner, `node:sqlite`
the database, `node:http` the server, and Node strips the TypeScript itself.
There is no build step and no `node_modules` at runtime, which is why deployment
is "copy the tree, set the environment, run node".

**Nothing knows where it is running.** Every path derives from
`STONEHASH_DATA_DIR` and every address comes from the environment. This box is a
test server; production is a different instance, and the same tree runs on both.

**The verifier shares no code with the producer.** `apps/core` emits proof
bundles; `packages/attest-verify` checks them; `apps/core` depends on it only as
a devDependency, so nothing shipping can import the checker. Two implementations
written separately against a published spec agreeing on real bytes is evidence.
One implementation agreeing with itself is not.

## Quick start

```bash
# Node >= 22 and (for anchoring) bitcoind on PATH
pnpm install

pnpm -r test          # 272 tests: conformance, agreement, API, rules, signatures, console, docs
pnpm -r typecheck

./deploy/regtest-node.sh start        # local chain, funded wallet, no faucet
cp apps/core/.env.example apps/core/.env   # then paste the printed BITCOIND_* values
pnpm --filter @stonehash/attest-playground build
pnpm --filter @stonehash/attest-docs build
pnpm --filter @stonehash/attest-console build
./deploy/run-core.sh                   # /playground/, /docs/ and /console/ on 127.0.0.1:8787

BASE=http://127.0.0.1:8787 ./deploy/smoke.sh   # issue → anchor → export → verify
```

Long-running, via the supervisor this host already uses:

```bash
pm2 start deploy/ecosystem.config.cjs   # reads apps/core/.env
pm2 save
```

## Playground

`apps/playground` verifies proof bundles **in the browser**. It imports
`@stonehash/attest-verify` and calls it directly, so the code a visitor watches
run is the code a regulator would install from npm. No document is uploaded, no
digest is transmitted, and no StoneHash endpoint is contacted — the network tab
stays empty after load and the page keeps working offline.

There is no bundler and no framework. The verifier has no dependencies and the
UI has no component library, so a bundler would have no module graph to flatten;
TypeScript's `rewriteRelativeImportExtensions` handles the one thing it was
still needed for. What ships is unminified ES modules, which for a tool whose
claim is "check this yourself" is part of the product rather than an oversight.

Six tabs: **Verify** (drop a bundle and the original), **Explore** (edit an
anchored document and watch link A break while B and C1 hold), **Anchor** (take
a digest through the free tier against the live chain), **Bank Review** and
**Corridor** (re-run a settlement policy and watch the six axes move
independently), **Evidence** (the Merkle fold, the BC01 byte layout and the
txid, all recomputed in-page).

Its sample is a real anchored bundle with a three-level Merkle path, generated by
`apps/core` against an actual chain — not a hand-written fixture.

## Developer Hub

`apps/docs` publishes what a third party needs to verify a proof without asking
us anything: the Quick Start, the OpenAPI 3.1 reference, the evidence
specification, the public test vectors, the SDK surface, and a security page
that states what the product does **not** claim.

Same construction as the Playground — no bundler, no framework, no dependency —
and for a sharper reason. The hub ships under `default-src 'none'; script-src
'self'`, so a CDN-loaded reference renderer would simply be blocked. A site
whose argument is "check this yourself" cannot ask the reader to execute a third
party's code while they do it, so the reference renderer is ninety lines in
`src/openapi.ts` and the Markdown renderer is its own file.

Two things keep it honest rather than merely present:

- **The reference cannot drift from the server.** `test/openapi.test.ts` reads
  the route table out of `apps/core/src/http/routes.ts` and compares it to
  `openapi.json`. Add a route without documenting it and the build goes red,
  naming the route. A hand-written spec drifts, and it drifts in the direction
  that flatters the product.
- **The specification is not copied.** `fixtures/bundle-schema.md` is published
  verbatim at build time. A second copy under `content/` would go stale the
  moment a field changed, and the stale one is what a regulator would read — so
  a test asserts the duplicate does not exist.

The anti-exaggeration rules of `docs/DESIGN.md §10` apply to the prose too: a
document that mentions regtest without stating that third-party chain
confirmation is unavailable there fails its test, as does one that promises a
compliance determination.

## Issuer signatures

Settlement evidence carries ECDSA P-256 signatures, and they are **verified**
rather than declared. That distinction is the reason this section exists:
`Signature.status` used to arrive in the evidence document as a claim and the
engine believed it, so the Bank Review screen reported `ISSUER VALID` because a
fixture said so, with no cryptography running anywhere.

Three things now make that failure mode unavailable:

- **Verification is a separate pass, and the engine refuses unverified input.**
  `verifyEvidenceSignatures()` computes each status and stamps a marker;
  `evaluate()` treats an unmarked signature as *not checked* and withholds the
  issuer axis. Forgetting to verify costs you the axis instead of silently
  granting it — the same rule the proof bundle applies to link C2.
- **Trust comes from the keyring, never from the document.** A signature
  claiming `ACCREDITED` resolves to whatever its key is actually worth. An
  unrecognised `keyId` is `UNKNOWN_KEY` and inherits nothing.
- **The fixtures are really signed, and CI checks they still are.** Each
  counterparty has its own key; `tools/sign-fixtures.mjs --check` fails the
  build if a fixture's content was edited without re-signing.

The demonstration keys' **private halves are published** in
`packages/attest-rules/keys/`. Anyone can forge these signatures, which is the
point: their trust level is pinned to `DEMO`, below anything a policy can
require, so every signature can verify and the issuer axis still reports
`UNKNOWN_ISSUER`. A verified signature and an established identity are two
findings, and they are rendered as two rows.

What the signature covers is the element's canonical JSON minus `signature`,
`digestVerified`, `attached` and `citedOnly`. The exclusions are deliberate:
the last three are submission and verification state rather than issuer
assertions, and covering them would let a *forgotten* invoice read as a *forged*
one — collapsing the distinction the completeness and issuer axes exist to draw.

Proof bundles carry no issuer signature. `bitcert-proof-bundle/v1` has no field
for one and its section set is closed, so adding it is a wire-contract change
affecting the independent verifier and all eight conformance fixtures — a
decision to take deliberately, not a gap to fill quietly.

## Sandbox Console

`apps/console` is where someone evaluating the product signs in. Signup is
**instant and ungated** — no approval queue and no sales call, because one
standing between a developer and their first API response is what loses an
evaluation.

One call provisions everything a first request needs: the org, an `sk_test_`
key, a registered demo issuer key, and **one worked attestation already in the
account**, so the first bundle export has something to export. An empty
dashboard with a "create your first attestation" button does not get someone to
a successful call in a minute; it just moves the blank page.

| | |
|---|---|
| Auth | Email + password. scrypt from `node:crypto`, per-account salt, cost parameters stored with the digest so they can be raised later without locking anyone out |
| Sessions | **Stored, not stateless.** A signed self-contained cookie cannot be revoked before it expires, which would make "sign out" a word the product used without meaning. The cookie carries a random token; the database holds its hash |
| Cookie | `HttpOnly`, `SameSite=Lax`, `Secure` under TLS. `Lax` is what makes the absence of a CSRF token safe rather than an oversight |
| Quota | 1,000 attestations per calendar month, 30-day retention. **The downloaded bundle never expires** |
| Scope | Sandbox only. The routes refuse to answer on `live`, where access is provisioned per contract |

The console surface is session-authenticated and kept separate from the keyed
API. The two have different callers and different threat models — a server
holding a secret key against a browser holding a cookie — and sharing one
surface would mean either the key API accepted cookies, giving every page on the
origin the ability to act as the customer, or the console shipped a long-lived
secret to the browser.

**It does nothing a customer could not do with curl.** The dashboard shows the
equivalent terminal commands beside each action, because a console that could do
more than the API would be demonstrating a product that does not exist.

The secret key is shown once, at the moment it is minted, and `dist.test.ts`
asserts the page never reaches for `localStorage`, `sessionStorage`, `IndexedDB`
or `document.cookie`. The service stores only a hash, so nothing could recover a
cached copy anyway — but caching it would put a credential somewhere the
customer did not choose.

Documents are hashed in the browser with WebCrypto and only the digest is sent;
the same test asserts no `FormData` or multipart body exists anywhere in the
client, so the upload path cannot reappear by accident.

### Not built, and why

OAuth (GitHub, Google) is the design's other listed signup option and needs
registered client credentials, which are deployment configuration rather than
code. Webhooks are a listed T2 feature and need delivery, retry and signing
machinery that is its own piece of work. Neither is stubbed.

There is **no password reset**, because nothing on this deployment sends mail.
The signup screen says so rather than offering a link that would not work.

## The four links

A proof bundle stands or falls on four separate claims, and they are always
reported separately — a single green tick would hide which one is missing.

```
 original ──(A: preimage)──▶ leaf_bytes ──(B: merkle)──▶ root ──(C: anchor)──▶ Bitcoin
```

| Link | Claim | Needs |
|------|-------|-------|
| **A** | this digest is *your* document | the original file |
| **B** | the digest is in this Merkle root | the bundle alone |
| **C1** | the anchor bytes belong to this txid | the bundle alone |
| **C2** | that txid is in a public block | a Bitcoin source **you** choose |

Links A, B and C1 are pure arithmetic and prove out offline, with no network and
no trust in StoneHash. C2 is the single chain-dependent step and the verifier
never performs it: the caller consults its own node or an explorer and merges the
result. Until then C2 reads `skip`, which means unverified, not fine.

### What `regtest` does and does not give you

The sandbox anchors to a private regtest chain. Links A, B and C1 verify there
exactly as they do on mainnet — they are mathematics, and the chain is irrelevant
to them. **C2 cannot be satisfied on regtest for anyone but us**, because we mine
the blocks. A regtest bundle is therefore a faithful exercise of the whole
pipeline and *not* a publicly verifiable proof.

This is not a labelling convention that can be forgotten. `bitcoin_network` is a
required field of the wire contract, so every conforming verifier reads it and
reports it, and `GET /v1/meta` states the limitation in words. A regtest proof
cannot be presented as a mainnet one.

Moving to mainnet is `ANCHOR_BACKEND=mainnet` against a funded node. Batching,
bundling and verification are untouched — that is what the `AnchorBackend` seam
is for.

## API

Thirteen operations. The full reference, with every error shape, is the
Developer Hub's API page — and it is checked against this table on every build,
so it cannot quietly drift.

| Method | Path | Key | Notes |
|-------:|------|:---:|-------|
| `GET` | `/healthz` | — | liveness |
| `GET` | `/readyz` | — | 503 when the chain is unreachable |
| `GET` | `/v1/meta` | — | network, key prefix, what this deployment can prove |
| `POST` | `/v1/sandbox/keys` | — | self-serve key, instantly, sandbox only |
| `POST` | `/v1/public/anchors` | — | **free tier**: anchor a digest with no account |
| `GET` | `/v1/public/anchors/:id` | — | status; the id is the only credential |
| `GET` | `/v1/public/anchors/:id/bundle` | — | the bundle, which outlives the record |
| `POST` | `/v1/attestations` | ✓ | submit a SHA-256; **the document is never uploaded** |
| `GET` | `/v1/attestations` | ✓ | list, scoped to the org |
| `GET` | `/v1/attestations/:id` | ✓ | status: `accepted → batched → submitted → confirmed` |
| `GET` | `/v1/attestations/:id/bundle` | ✓ | the proof bundle |
| `POST` | `/v1/settlements/reconcile` | ✓ | evaluate evidence against a stated policy; **stateless** |
| `POST` | `/v1/settlements/bundle` | ✓ | the evidence archive, assembled per request and never stored |

The settlement endpoints store nothing: evidence and policy arrive in the
request, the verdict and the archive are returned, and nothing is written. A
reviewer's case data never rests on our disk.

Sandbox and production run the same code. They differ in the database file, the
anchor backend and the key prefix (`sk_test_` / `sk_live_`) — nothing branches on
the environment, because a sandbox running different code would prove nothing
about production.

## Tests worth knowing about

| File | What it guards |
|------|----------------|
| `attest-verify/test/conformance.test.ts` | The producer's own published fixtures — five that must pass and **three tampered ones that must fail**. Drift on either side goes red. |
| `attest-verify/test/sha256.test.ts` | NIST vectors, the spec's frozen vector, and a differential check against `node:crypto`. |
| `attest-verify/test/portability.test.ts` | No runtime dependencies and no `node:` import in `src/`, so the browser build cannot rot. |
| `core/test/roundtrip.test.ts` | Producer output verified by the independent verifier, batch sizes 1–16, with tampering attributed to the right link. |
| `core/test/api.test.ts` | Real server, real SQLite: lifecycle, org isolation, duplicate and malformed input. |
| `playground/test/dist.test.ts` | The **built** output: every emitted import resolves, no `.ts` specifier survives, and the emitted verifier still verifies. There is no bundler to catch an emit bug, so this does. |
| `docs/test/openapi.test.ts` | The API reference against the server's own route table, read out of `routes.ts`. An undocumented route fails the build **by name**. |
| `docs/test/content.test.ts` | Every published document rendered: no unescaped markup, every table and code sample in the wire contract survives, and no document oversells (regtest caveat present, no compliance claim). |
| `docs/test/dist.test.ts` | The hub's built output: every element the script addresses exists in the page, nothing loads from a remote origin, and the reference stays a document rather than growing a request console. |
| `attest-rules/test/signature.test.ts` | Real ECDSA: a fixture signature verifies, an edited amount breaks it, an unknown key inherits no trust — and **a declared status nobody computed can never reach a VALID issuer axis**. |
| `core/test/console.test.ts` | Accounts against a real server: one tenant cannot read another's records, the secret key is unreadable after signup, rotation kills the old key immediately, and the quota reports when it resets. |
| `console/test/dist.test.ts` | The built console never persists a credential, never posts a file, and paints only `confirmed` with the success colour. |

## Not built, deliberately

No message bus, gateway, Helm chart or service mesh. No OP_RETURN v30 encoder —
it is patent-pending and `BC01` (53 bytes, published layout) carries everything a
bundle needs. No mainnet hot wallet: bitcoind holds the keys and does the funding
and signing, so no private key enters this process on any network. No
OpenTimestamps — anchoring runs on our own pipeline.

No Scalar, Redoc or Docusaurus in the Developer Hub: all three load from a CDN,
which the hub's own CSP forbids and its offline guarantee rules out. No "try it"
console on the API reference either — a request button on a documentation page
invites pasting a live key into a browser tab, and the Playground is where the
API gets exercised, holding no keys while it does.
