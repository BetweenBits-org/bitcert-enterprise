# Golden vectors

What the TypeScript SDK (`packages/attest-remit`) answers for a fixed set of
inputs. The Java SDK is held to the same answers: the same payments read out
of the same bytes, the same refusals with the same code, field and words, the
same payment ids and digests, the same status and the same `pacs.002`.

They are written by `tools/make-golden.mjs` from the cases in
`tools/golden-cases.mjs`; nothing here is edited by hand.

    node sdks/attest-remit-java/tools/make-golden.mjs          # write
    node sdks/attest-remit-java/tools/make-golden.mjs --check  # fail when the SDK answers differently now

Five files have generators of their own, named in their rows, each with the
same `--check`. Two of them read what another wrote, so the order to write
them in is `make-golden.mjs`, `make-verdict-golden.mjs`,
`make-rules-golden.mjs`, `make-platform-golden.mjs`.

| File | A case is | Expected |
|---|---|---|
| `parse.json` | `input`: `{ as: "bytes", base64 }`, `{ as: "string", text }`, or for an input too large to store `{ as: "bytes" \| "string", repeat: { prefix?, text, times } }` — `prefix`, then `text` written `times` times, handed over as Latin-1 bytes or as a string | `expect.payments` — `parseSwiftMessages(input)` as `JSON.stringify` writes it (a field the SDK leaves undefined is absent) — with `expect.derived[i]` for payment *i*: its payment id per institution, its content digest, its ISO 20022 field names. Or `expect.error`: `{ name, code, field?, message }`. `single` is `parseSwiftMessage(input)` (the index it returns, or the error); `beyond` is `parseSwiftMessage(input, { index: payments.length })` |
| `mapping.json` | `parse` names a case of `parse.json`, `index` the payment in it, `options` what `mapSwiftPayment` is given | `expect`: `fields`, `issues`, `unmapped`, `input` (`null` when there are issues) and, when there are issues, `error` — the `SwiftMappingError` a caller gets |
| `status.json` | `view`: a settlement view; `options`: what `buildPacs002` is given (`createdAt` is fixed) | `expect.status` (`swiftStatusOf`), `expect.sourceMessage` (`sourceMessageOf`, or `null`), `expect.pacs002` (the report, as text). `table` is `SWIFT_STATUS_TABLE` |
| `scenarios.json` | One `RemitClient` (`client`; its key is `testKey` of `signing.json`, its `apiKey` the case's when given) against one stand-in platform (`platform.rules`, `platform.quote`) holding the case's `ledger` first. The stand-in the vectors are generated against is not a copy of the platform's "one message, one settlement" rule but the platform's own store on an in-memory database; `platform.rules` states that rule in words for a port's stand-in. `steps`, in order: `message` (`{ parse: <case of parse.json> }` or `{ as: "string", text }`) handed to `submitSwift` with `options` (`index`, `paymentId`, `supplement`; `supplementByAccount` is handed over as a lookup by the debtor's account); `race`: a string — the POST is answered 409 with that error after the settlement is kept — or `{ taken: <settlement> }` — another process's settlement is judged and kept just before this POST is looked at; or `cancel: { paymentId, reason }` | per step `expect.outcome`: `{ paymentId, state, already }` (a cancel: `{ paymentId, state }`) or `{ error: { name, code?, field?, message, status?, existingPaymentId?, ground? } }`, `name` the class (`SwiftMessageError`, `SwiftMappingError`, `RemitApiError`), `existingPaymentId` and `ground` what a refusal for a message that already has a settlement names; `posts` and `quotes`: the POSTs to `/v1/settlements` (the refused ones too) and `/v1/quotes` made so far in the case; `searched`: the query of each `GET /v1/settlements` the step made, in order, without `limit` and `cursor` (`source_uetr=<uuid>`); for a step that posted, `posted`: `idempotencyKey`, `payment_id`, the posted `bankInstruction.sourceMessage`, and `bank_authorization`'s `instruction_ref` and `uetr` |
| `signing.json` | values, event payloads, evidence elements | `jcs[i].utf8Hex` (or `error`), `events[i].signingBytesHex`, `elements[i].digest` and `.signingBytesHex`; `signedByTypeScript` holds events and elements signed with `testKey`, which the Java SDK must verify. Signatures are random, so the ones on disk are kept while they still verify |
| `status-views.json` | Written by `tools/make-status-views-golden.mjs` (same `--check`). `view`: any JSON at all as a settlement view — the views the reference SDK's hardening test (`packages/attest-remit/test/hardening-status.test.ts`) uses, and the first 300 it generates from its fixed seed — stored as JSON holds it; `options`: `messageId`, `createdAt` | `expect.status`, `expect.sourceMessage` (or `null`) and `expect.pacs002` as in `status.json`. Where `options.createdAt` is not a time in the platform's form the report states when it was made: the text then has `<CreDtTm><now></CreDtTm>`, and the Java test puts `<now>` in place of its own creation time before comparing. No view ends in an exception, in either SDK |
| `verdict.json` | Written by `tools/make-verdict-golden.mjs` (same `--check`; nothing in it is signed anew, so every run writes the same file). A case is a base document (`bases`) and a list of changes — `{ at: [path], set }` or `{ at: [path], unset: true }`, applied in order. `engine`: `{ evidence, policy }`, the evidence as the signature pass leaves it. `signatures`: `{ evidence, registry }`. `packages`: an evidence response. `dates`: text, with the `form` it is written in (`standard`: the language standard's date-time format with a zone, or a date alone; `local`: a time without a zone; `other`; `none`: no digit in it). `parties`: two names | `engine`: `expected.states` (the six axes, in order) and `expected.findings` (each as `axis:code:severity`, in the order the rules ran) — what `evaluate` of `packages/attest-rules` answers — or `threw`: the Java SDK must then refuse too, and never answer. `signatures`: the signature of every element after `verifyEvidenceSignatures`, or `threw`. `packages`: the `signatures` and `verdict` checks of `verifyEvidencePackage`, `{ ok, detail }`, or `threw`. The stated verdict is compared with the re-run axis by axis — the same axes, each with the same state; the order a package lists its axes in is not compared — and a difference is one sentence in both SDKs: both verdicts in the rules' order, then any other axis the package states by name, and in words any it names without a state. `dates`: `ms` as `Date.parse` answers (`null` for no date); the Java SDK reads `standard` to the same value, refuses `local` and `other`, and reads `none` as no date. `parties`: `equal` under `normalized` matching. The few cases the Java SDK is stricter on by design are named in `VerdictEngineTest` |
| `rules.json` | Written by `tools/make-rules-golden.mjs` (same `--check`; run after `make-verdict-golden.mjs`, whose `bases` and cases it reads; nothing in it is signed anew, so every run writes the same file). One case to a line. `engine`: a case `from: "verdict.json"` is the engine case of that name in `verdict.json`; one with `base` and `ops` is that base of `verdict.json` with the changes applied; otherwise `evidence` and `policy` are stated. `policies`: `policy`. `signatures`: the evidence — `from: "verdict.json"` (the signature case of that name), `base` and `ops` (against `{ evidence }` of the sandbox base) or `evidence` — and `keyring`, the entries `Rules.keyring` takes: `keyId`, `issuer`, `trustLevel`, and `publicKeyJwk` or `publicKeySpki`. `instants`: `[text, ms]` pairs — `shaped` is text of the shape `Rules` reads (`shape`, a regular expression), `other` is text of any other shape. `table`: `values` — objects with a member of their own named `toString` (alone, in lists) and the look-alikes with `valueOf` — each put at every one of `positions` of the sandbox base: for `engine` under each of `contexts` (changes applied first), for `policies` in the sandbox policy (`[]` is the policy itself), for `signatures` in the sandbox evidence, against `keyring` | `engine`: `result` — the whole `MatchingResult` of `evaluate`, as `JSON.stringify` writes it — or `threw`: `{ message, engine }`. `engine: false` is the reference's own sentence, with which `Rules` refuses to the letter (`invalid_policy`, `invalid_amount`); `engine: true` is the JavaScript engine failing inside the reference, where `Rules` refuses in words of its own (`unreadable_evidence`, `unreadable_policy`) and never answers. A case that carries `reference` as well is one where the reference's answer rests on a spelling of a time that `Rules` does not read: `reference` is what the reference answers today, `result` the same with such a time unparseable — which is what `Rules` must answer. `policies`: `problem` (`null`, or as `threw`), `canonical` (`canonicalPolicy`) and `digest` (`policyDigest`). `signatures`: `expected.evidence` — the whole evidence after `verifyEvidenceSignatures` — or `expected.threw`. `instants`: `ms` is `Date.parse(text)` on a machine in UTC, `null` for no date; `Rules` reads `shaped` to the same value, and `other` as no date whatever the engine answers. `table`: a cell (`cells[context][position][value]`; for `policies` and `signatures` `cells[position][value]`) is the SHA-256 of the reference's answer written as JSON — the whole result of `evaluate`; for `policies` the policy's digest, a space, then `taken` or the refusal; for `signatures` the whole evidence after the pass — or the refusal: `engine: …` where the JavaScript engine fails (`Rules` refuses, in words of its own), `refused: …` where the reference refuses in its own sentence (`Rules` says the same). The engine can make no text and no number of an object with a member of its own named `toString`, nor of a list holding one; `tools/make-rules-golden.mjs --cell …` prints a cell's answer in full. Results are compared as text, written as JavaScript writes JSON: member order and the spelling of numbers included |
| `conventions.json` | Written by `tools/make-platform-golden.mjs` (same `--check`; run after `make-golden.mjs`, whose test key it signs with) from the platform's own code (`apps/core/src/remit`). One case to a line. `events`: `payload`. `elements`: `element`. `signedByPlatform`: events (`payload`, `sig`) and elements (`signed`) signed by the platform's `signEvent` and `signEvidenceElement` under `key`. `verifyEvent`: `payload`, `sig`, `spki`. `commitments`: `package`, `nonce`. `base64.decode`: `text`; `base64.encode`: `hex` | `events`: `signingBytesHex` (`eventSigningBytes`) and `signingDigest`, their SHA-256 — or `threw`. `elements`: `signingBytesHex` (`signedBytes`), `signingDigest` (`signedDigest`) and `contentDigest` (`elementDigest`) — or `signingThrew`, `digestThrew`. `signedByPlatform`: each has to verify in the Java SDK. `verifyEvent`: `expected`, what the platform's `verifyEvent` answers (`threw` where it fails inside its engine); `java` is stated where the Java SDK answers otherwise on purpose — a key that is not ECDSA P-256 verifies nothing (`otherKey` is such a key, with a signature of its own kind over the first event), and an envelope that is not there is not valid. `commitments`: `value` (`packageCommitment`), or `threw`; `java: "invalid_nonce"` where the Java SDK refuses a nonce that is not hex and the platform uses the part of it that is. `base64.decode`: `forgiving` — the bytes `fromBase64Url` reads, as hex, `null` where it throws — and `lenient`, the bytes `Buffer.from(text, "base64")` reads; `base64.encode`: `base64url`. Signatures are random, so the ones on disk are kept while the platform still verifies them |
| `travel-rule.json` | Written by the same run of `tools/make-platform-golden.mjs`. `missing`: `compliance`, the party data a bank submits. `messages`: `compliance` and `context`. `kdf`: `z` (hex), `bits`, `alg`, `apu`, `apv`. `recipient`: the key the tests encrypt to — the public half of the test key of `signing.json` | `required`: `REQUIRED_TRAVEL_RULE_FIELDS`. `missing`: what `missingTravelRuleFields` lists, or `threw`. `messages`: `message` (`buildIvms101`, as `JSON.stringify` writes it), `json` — that text, which is what the platform encrypts — and `digest`, the SHA-256 of the message's canonical form, which the evidence carries (`digestThrew` where it has none); or `threw`. `kdf`: `key` (hex), what `concatKdf` derives; the first case is the vector of RFC 7518, Appendix C |
| `anchor.json` | `bundle`: a proof file — the conformance fixtures under `fixtures/conformance`, each as issued and with one thing changed, and transactions crafted to push the anchor payload each way a script can. Written by `tools/make-anchor-golden.mjs` (same `--check`), not by `make-golden.mjs` | `expected.verified` and `expected.checks` — what the reference verifier (`verifyBundle` of `packages/attest-verify`) answers, each check as `id:state`, in its order. `java` is `same` (the Java SDK's `AnchorProof` must answer exactly that) or `unsupported` (a form of proof file the Java SDK does not re-verify: it must say so and never pass it) |

A JSON number in these files is always an integer — but for the values
`jcs` is pinned on in `signing.json`, and for `rules.json`,
`conventions.json` and `travel-rule.json`, which hold numbers of every kind
on purpose. Key order inside an object is the order the TypeScript code
built it in; compare values, not text — except `pacs002`, digests and hex,
and the results of `rules.json` and the messages of `travel-rule.json`,
which are compared as text.

The tests put every case of those three files to the SDK twice: with its
numbers as the SDK's own reader holds them (`Long`, `BigDecimal`), and with
every number held as a `Double`, which is how the platform's JSON reader
hands numbers over. A number is its value — to the reference, `1`, `1.0` and
`1e0` are one number — so both have to give the recorded answer, down to the
signature over an element that holds one.

Two things no stored file can hold are checked by running both sides at
once, after `./run-tests.sh` has built what they run:

    node sdks/attest-remit-java/tools/check-java-made.mjs [java ...]             # what the Java SDK signs and encrypts, verified and opened by the platform's code
    node sdks/attest-remit-java/tools/diff-fuzz-rules.mjs [count] [seed] [java]  # Rules beside the reference engine, on settlements changed at random

A signature and a ciphertext are other bytes on every run, so the first
makes them and checks them in one go, on each Java runtime named. The second
is repeatable for a given seed, and exits non-zero on any difference.
