# 준비금 증명: 잔고 파일 준비

귀사 원장에서 잔고 파일 하나를 내보내 SDK에 넘기면 스냅샷이 앵커링됩니다
— 호출은 [준비금 증명](#por)의 "스냅샷 앵커링"에 있습니다. 이 페이지는 그
파일에 관한 것입니다: 어떤 모양이어야 하는지, 원장에서 어떻게 내보내는지,
무엇을 잔고로 세는지, 파일에 문제가 있으면 어떻게 알려 주는지, 그리고
앵커링 뒤 무엇을 보관하는지.

잔고 파일과 계정 정보는 귀사 서버를 떠나지 않습니다. 플랫폼은 원장을
받지도, 귀사 DB에 접속하지도 않습니다. 플랫폼이 받는 것은 루트·자산별
총액·계정 수가 담긴 선언문과 그 서명입니다.

SDK를 붙이기 전에 파일부터 확인하고 싶다면, 콘솔의 **준비금 증명** 화면에
같은 파일을 넣어 볼 수 있습니다. 브라우저 안에서 같은 코드로 읽어 루트를
만들고 앵커링까지 하며, 파일은 서버로 올라가지 않습니다. 이 화면은 계정
100,000개까지 다루고, 더 큰 원장은 SDK로 귀사 서버에서 앵커링합니다.

## 파일 형식

UTF-8 파일입니다. **표준은 계정마다 한 줄, 자산마다 한 열인 CSV입니다.**

```
account_id,BTC,ETH,USDT
U-100001,0.50000000,12.5,
U-100002,,,1500.25
```

첫 열이 `account_id`, 나머지 열의 이름이 자산 기호입니다. 보유하지 않은
자산은 칸을 비우거나 0으로 적습니다. 내보내기를 새로 만든다면 이 형태로
만드십시오 — 예시 파일은 SDK의 `samples/balances.wide.csv`입니다.

이미 다른 모양으로 내보내고 있는 파일이 있다면 고치지 않고 쓸 수 있습니다.
아래 세 형태도 읽으며, 같은 원장은 어느 형태로 내보내도 같은 루트가
나옵니다. CSV는 첫 줄(헤더)을 보고 자동으로 구분하고, 옵션
`layout: 'wide' | 'long' | 'sheet'`로 직접 지정할 수도 있습니다(`wide`가
표준 형태입니다). 각 형태의 예시가 SDK의 `samples/`에 있습니다.

**세로형 CSV — 계정과 자산마다 한 줄**

```
account_id,asset,balance
U-100001,BTC,0.50000000
U-100001,ETH,12.5
U-100002,USDT,1500.25
```

DB에서 `GROUP BY` 한 번으로 나오는 모양입니다.

**시트형 CSV — 계정마다 한 줄, 자산마다 잔고 열과 부채 열**

```
id,e_BTC,d_BTC,e_ETH,d_ETH,e_USDT,d_USDT
U-100001,0.50000000,0,12.5,0,,0
U-100002,,0,,0,1500.25,0
```

자산마다 잔고와 부채를 나란히 둔 잔고표를 이미 내보내고 있다면 그 파일을
그대로 쓸 수 있습니다. 헤더에 같은 자산의 `e_<자산>`과 `d_<자산>`이 함께
있으면 이 형태로 읽습니다.

- 계정 열은 `account_id`, 없으면 `id`입니다.
- `e_<자산>`이 그 자산의 잔고입니다.
- `d_<자산>`(부채)은 모든 줄에서 비어 있거나 0이어야 합니다. 0이 아닌 줄이
  하나라도 있으면 `debt_not_supported`로 거부합니다 — 부채를 잔고에서
  빼지도, 못 본 척하지도 않습니다(아래 "잔고로 세는 것").
- 같은 자산의 다른 열(`<자산>`, `vl_<자산>`, `m_<자산>`, `pm_<자산>`)과
  `rn`, `total_net_balance_usdt`는 읽지 않고, 건너뛴 열로 보고합니다.

**JSON — 계정 배열** (확장자가 `.json`이면 이 형태로 읽습니다)

```json
[
  {"id": "U-100001", "assets": {"BTC": "0.50000000", "ETH": "12.5"}},
  {"id": "U-100002", "assets": {"USDT": "1500.25"}}
]
```

- 금액은 **문자열**로 적습니다. JSON 숫자(`0.5`)는 `amount_not_text`로
  거부합니다 — 숫자는 잔고의 자릿수를 모두 담지 못하고, 어느 자리가
  사라졌는지도 알 수 없기 때문입니다.
- 계정은 `id`(또는 `account_id`), 잔고는 `assets`(또는 `balances`)에
  적습니다. 한 계정에 두 이름이 함께 있으면 어느 쪽도 고르지 않고
  거부합니다.
- 한 객체 안에 같은 이름이 두 번 나오면 `json_duplicate_key`로
  거부합니다. JSON은 뒤의 값만 남기므로 앞의 잔고가 말없이 빠지기
  때문입니다.
- 보유하지 않은 자산은 적지 않아도 됩니다. 그 밖의 필드는 건너뛰고
  보고합니다.
- 문제의 위치는 줄 번호가 아니라 배열에서 몇 번째 계정인지로 알려 줍니다.
- 파일 전체를 한 번에 읽습니다. 계정이 수백만이면 CSV가 맞습니다.

| 항목 | 규칙 |
|---|---|
| `account_id` | 귀사가 사용자에게 알려 줄 수 있는 계정 식별자. 파일에 적힌 그대로 사용하며 앞뒤 공백이 있으면 거부합니다(잘라 내면 다른 식별자가 되기 때문입니다). 256바이트 이하, 줄바꿈·제어문자 불가 |
| 자산 기호 | 자산 열의 이름(세로형에서는 `asset` 값)이 `assets`에 적은 기호와 대소문자까지 일치해야 합니다. 목록에 없는 자산이 나오면 오류입니다 — 조용히 빼면 총액이 줄어들기 때문입니다 |
| 금액 | 0 이상의 수. 표기 방식은 `amounts`로 반드시 밝힙니다(아래) |
| 한 계정 | 한 줄만(세로형은 한 계정·자산에 한 줄). 두 번 나오면 오류입니다 — 합산이 맞는지는 귀사 쿼리에서 정합니다 |
| 빈 칸 | "보유 없음"(0). 세로형에서는 오류 |
| 그 밖의 열 | `ignoreColumns`에 적은 열만 무시합니다 — 적지 않은 열은 자산일 수 있기 때문입니다. 세로형은 그 밖의 열을 무시하고 보고합니다 |
| 구분자·따옴표 | 쉼표. 다른 구분자는 `delimiter`(탭은 `'\t'`). 값에 쉼표가 있으면 큰따옴표로 감쌉니다 |

**금액 표기 — `amounts`는 생략할 수 없습니다.** `1`이 1 BTC인지 1
사토시인지는 귀사 원장만 압니다.

| 값 | 파일에 적는 방식 | 예 (BTC 0.5) |
|---|---|---|
| `decimal` | 사람이 읽는 단위의 소수 | `0.5`, `0.50000000` |
| `base` | 최소 단위의 정수 | `50000000` |

변환은 정확하거나 거부됩니다. 반올림·절삭은 없습니다 — 자산의 자릿수보다
아래에 0이 아닌 숫자가 있으면(`0.123456789` BTC) 오류입니다. 지수
표기(`1e-8`), 천 단위 구분(`1,000`), 음수도 오류입니다.

계정 열의 이름이 다르면 파일을 고치지 않고 이름을 알려 줄 수 있습니다:
`columns: { account: 'user_id' }` (세로형은 `asset: 'currency'`,
`balance: 'amount'`도).

**자산 목록.** 거래소마다 다루는 자산이 다르므로 목록은 귀사가 정합니다.
자산 이름은 영문·숫자로 시작하고 영문·숫자·`.`·`_`·`-`로 이루어진 32자
이하의 기호이며(`BTC`, `1INCH`, `BTC.b`), 소수 자릿수는 0에서 36까지입니다.
몇 개면 코드에 그대로 적고, 수십·수백 개면 파일로 두고 읽습니다
(`assets: readAssetList('assets.csv')`):

```
symbol,decimals
BTC,8
ETH,18
USDT,6
```

목록은 파일에 나오는 자산을 모두 담아야 합니다 — 목록에 없는 자산이
나오면 오류입니다. 반대로 아무도 보유하지 않은 자산이 목록에 있는 것은
괜찮습니다(세로형이 아니면 그 자산의 열이 비어 있더라도 있어야
합니다): 선언문에는 총액 0으로 적히고, 루트는 그 자산을 목록에 넣든
빼든 같습니다.

## 원장에서 내보내기

플랫폼은 귀사 DB에 접속하지 않습니다. 귀사가 쓰는 DB 클라이언트로 아래
모양의 결과를 CSV로 내보내면 됩니다. 테이블·열 이름과 자산 세 개는 귀사
원장에 맞게 바꾸십시오.

```sql
-- PostgreSQL
BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY;
SELECT btrim(user_id::text) AS account_id,
       SUM(CASE WHEN currency = 'BTC'  THEN available + locked ELSE 0 END)::text AS "BTC",
       SUM(CASE WHEN currency = 'ETH'  THEN available + locked ELSE 0 END)::text AS "ETH",
       SUM(CASE WHEN currency = 'USDT' THEN available + locked ELSE 0 END)::text AS "USDT"
FROM balances
GROUP BY user_id;
COMMIT;
```

```sql
-- MySQL / MariaDB
SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
START TRANSACTION WITH CONSISTENT SNAPSHOT;
SELECT TRIM(CAST(user_id AS CHAR)) AS account_id,
       CAST(SUM(CASE WHEN currency = 'BTC'  THEN available + locked ELSE 0 END) AS CHAR) AS BTC,
       CAST(SUM(CASE WHEN currency = 'ETH'  THEN available + locked ELSE 0 END) AS CHAR) AS ETH,
       CAST(SUM(CASE WHEN currency = 'USDT' THEN available + locked ELSE 0 END) AS CHAR) AS USDT
FROM balances
GROUP BY user_id;
COMMIT;
```

자산 열의 이름은 `assets`의 기호와 대소문자까지 같아야 합니다.
PostgreSQL은 따옴표가 없으면 열 이름을 소문자로 바꾸므로 `"BTC"`처럼
감쌉니다. 자산이 많아 SELECT 목록을 손으로 쓰기 어렵다면 자산 목록에서
쿼리를 생성하거나, 계정·자산마다 한 줄(세로형)로 내보내십시오 — 자산
목록 없이 `GROUP BY user_id, currency` 하나로 나오고, 그대로 읽습니다. 그
쿼리와 Oracle·SQL Server용 쿼리는 SDK의 `samples/export-queries.sql`에 있습니다.
어느 DB든 쿼리가 지켜야 할 것은 네 가지입니다.

1. **계정마다 한 줄.** 한 사용자의 지갑이 여럿이면 쿼리에서
   합산합니다(`GROUP BY`).
2. **돌려줄 의무가 있는 잔고 전부.** 주문에 묶인 잔고, 출금 대기 중인
   잔고도 사용자 몫입니다(`available + locked`).
3. **금액은 문자열로.** 부동소수점 타입을 거치면 자릿수가 바뀝니다.
4. **한 시점.** 내보내기 전체를 하나의 일관된 읽기 트랜잭션에서 수행하고,
   그 시각을 `asof`에 적습니다.

## 잔고로 세는 것

무엇을 부채로 볼지는 귀사가 정하고, 정한 규칙을 기록해 두십시오. SDK는
받은 파일을 그대로 합산할 뿐 판단하지 않습니다.

- **음수 잔고**는 거부됩니다. 마진 부채나 초과 인출 계정은 귀사 규칙에
  따라 정리하거나 제외한 뒤 내보내십시오. SDK가 대신 0으로 바꾸지
  않습니다.
- **0 잔고**는 그대로 받습니다. 0 잔고 계정을 포함하면 그 사용자도 "0으로
  포함됨"을 확인할 수 있고, 제외하면 그 사용자에게는 증명을 발급할 수
  없습니다.
- **부채**는 빼지 않습니다. 스냅샷은 각 계정에 돌려줄 잔고를 말하며,
  빌린 금액을 상계한 순자산을 말하지 않습니다. 시트형 파일의 부채 열은
  모든 계정에서 0이어야 하고, 0이 아닌 계정이 있으면 파일 전체를
  거부합니다. 상계한 값을 증명하려면 계정마다 담보가 충분한지도 함께
  증명해야 하는데, 해시 트리만으로는 그것을 보일 수 없습니다.
- **파일에 없는 계정**은 루트에 없습니다. 루트는 파일에 든 것만
  말합니다.

## 파일에 문제가 있을 때

문제가 하나라도 있는 파일로는 루트를 만들지 않습니다. `anchorBalanceFile`은
아무것도 쓰거나 보내지 않고 `PorLedgerError`를 던지며, 오류의
`report.problems`에 문제마다 줄 번호(`line`)·코드(`code`)·설명(`message`)이
들어 있습니다. 앵커링하지 않고 파일만 검사하려면 읽기만 합니다:

```ts
import { fromBaseUnits, readLiabilitiesCsv } from './packages/attest-por/src/index.ts';

const assets = [{ symbol: 'BTC', decimals: 8 }, { symbol: 'ETH', decimals: 18 }, { symbol: 'USDT', decimals: 6 }];
const { report } = await readLiabilitiesCsv('packages/attest-por/samples/balances.wide.csv', { assets, amounts: 'decimal' });

console.log(report.ok, report.layout, report.accounts);          // true 'wide' 12
for (const a of assets) console.log(a.symbol, fromBaseUnits(report.totals[a.symbol] ?? '0', a.decimals), report.holders[a.symbol]);
for (const p of report.problems) console.log(p.line, p.code, p.message);
```

**총액을 귀사 원장의 총액과 대조하십시오.** 이 숫자가 그대로 선언문에
들어가 서명됩니다. JSON 파일은 `readLiabilitiesJson`으로 읽고, 문제의
위치는 줄 번호 대신 배열에서 몇 번째 계정인지로 알려 줍니다.

| 코드 | 뜻 | 조치 |
|---|---|---|
| `amount_precision` | 자산의 자릿수보다 정밀한 값 | `assets`의 자릿수를 확인하거나 원장 값을 확인 |
| `amount_negative` | 음수 | 귀사 규칙에 따라 정리·제외 후 내보내기 |
| `amount_exponent` · `amount_grouping` · `amount_format` | 지수 표기, 천 단위 구분, 숫자가 아닌 값 | 금액 열을 문자열로 변환해 내보내기 |
| `amount_fraction_in_base` | `base`인데 소수점이 있음 | `amounts: 'decimal'` |
| `unknown_asset` | `assets`에 없는 자산 | 목록에 추가하거나 쿼리에서 제외 |
| `duplicate_row` · `duplicate_account` | 같은 계정(·자산)이 두 번 | 쿼리에서 합산 |
| `account_whitespace` · `account_empty` | 식별자 앞뒤 공백, 빈 식별자 | 쿼리에서 `TRIM` |
| `header_*` | 헤더가 어느 형태와도 맞지 않음, 목록에 없는 자산의 열, 목록의 자산에 열이 없음 | 열 이름을 맞추거나 `columns`·`layout`으로 지정 |
| `debt_not_supported` | 시트형에서 부채(`d_`)가 0이 아닌 계정 | 위 "잔고로 세는 것" |
| `amount_not_text` | JSON에서 금액이 숫자로 적힘 | 금액을 문자열로 내보내기 |
| `json_syntax` · `json_shape` · `json_duplicate_key` | JSON이 아님, 계정 배열 형태가 아님, 한 객체에 같은 이름이 두 번 | 위 "파일 형식"의 JSON 예시와 대조 |
| `csv_syntax` | 따옴표 짝이 맞지 않음 | CSV로 다시 내보내기 |
| `file_encoding` | UTF-8이 아님 | UTF-8로 다시 내보내기 |
| `too_large` (오류의 `code`) | 이 실행이 쓸 수 있는 메모리를 넘는 규모 | 아래 "확인된 규모" |


## 보관: 증명 파일과 잔고 파일

앵커링이 남기는 것은 **증명 파일 하나**입니다(`proofFile`에 준 경로, 권한
0600). 보관할 것은 이 파일과, 앵커링에 쓴 잔고 파일 그대로 — 두
가지뿐입니다. 콘솔의 준비금 증명 화면이 내려 주는 증명 파일도 같은
형식이라 SDK가 그대로 열고, SDK가 만든 증명 파일은 콘솔의 검증 화면에서 원본
잔고 파일과 맞춰 볼 수 있습니다.

| 증명 파일에 든 것 | 내용 |
|---|---|
| `statement` · `sig` · `snapshot_id` | 서명해 제출한 선언문과 그 서명, 플랫폼이 준 스냅샷 ID |
| `seed` | 계정별 솔트를 파생한 32바이트 시드 — **이 파일의 유일한 비밀값** |
| `source` | 잔고 파일의 이름·크기·SHA-256, 읽은 형태(`layout`)와 금액 표기(`amounts`) |

계정도 잔고도 들어 있지 않지만 시드가 들어 있으므로, 잔고 파일과 같은 곳에
두고 공개하지 마십시오. **두 파일 중 하나라도 잃으면 그 스냅샷의 사용자
증명을 더 이상 발급할 수 없습니다** — 앵커된 루트는 유효하지만 아무도 확인할
수 없게 됩니다. 백업 대상에 넣으십시오.

두 파일이 있으면 스냅샷이 그대로 다시 만들어집니다([준비금 증명](#por)의
"사용자 증명 발급"). 계정 식별자는 해시로, 잔고는 계정별 솔트와 함께
해시되어 트리에 들어갑니다 — 식:

```
user_ref_hash = SHA256("STONEHASH-POR-USER-V1\n" + exchange_id + "\n" + account_id)
salt          = HMAC-SHA256(seed, account_id)
```

트리는 계정이 실제로 보유한 잔고만 적습니다(선언문의 `tree.algo`:
`merkle-sum-sha256-v2`). 0인 잔고와 아무도 보유하지 않은 자산은 트리에
자리를 차지하지 않으므로, 상장 자산이 수백 종이어도 트리의 크기는 계정이
가진 잔고의 수를 따릅니다. 이전 형식(`merkle-sum-sha256-v1`)으로 만든
스냅샷과, 이전 버전의 SDK가 스냅샷마다 남기던 폴더(`leaves.jsonl` 등)는
그대로 접수·검증되고 계속 읽습니다(`loadTreeDir`).

## 확인된 규모

트리는 메모리에서 만들어집니다. 필요한 메모리는 계정 수와, 계정들이 실제로
보유한 잔고의 수를 따릅니다 — 상장만 하고 보유가 드문 자산은 거의 비용이
없습니다.

| 목록의 자산 수 | 계정당 보유 자산(평균) | 받는 계정 수(약) — Node 기본 메모리 설정 |
|---|---|---|
| 3 | 3 (전부) | 1,050,000 |
| 50 | 4 | 740,000 |
| 500 | 5 | 540,000 |
| 500 | 20 | 250,000 |

표의 값은 SDK가 시작하기 전에 계산하는 추정이며, 한도를 넘는 입력은 만들기
전에 알려 줍니다(`PorLedgerError`, `code: 'too_large'`). 실측한 범위는
다음과 같습니다(메모리 16GB 서버, 표준 형태의 파일).

| 원장 | 잔고 파일 | 앵커링 호출 | 스냅샷 다시 열기 | 최대 메모리 | 사용자 증명 한 건 |
|---|---|---|---|---|---|
| 계정 100만 · 자산 3종(전부 보유) | 46MB | 63초 | 61초 | 2.9GB | 4KB |
| 계정 30만 · 자산 500종(계정당 5종) | 163MB | 37초 | 40초 | 2.1GB | 146KB |
| 계정 10만 · 자산 500종(계정당 20종) | 71MB | 28초 | 29초 | 1.4GB | 153KB |
| 계정 10만 · 자산 500종(계정당 5종) | 54MB | 12초 | 13초 | 1.1GB | 122KB |
| 계정 10만 · 자산 3종(전부 보유) | 5MB | 5초 | 6초 | 0.7GB | 3KB |

"앵커링 호출"은 파일을 읽어 증명 파일을 쓰기까지이며 네트워크 시간은
뺐습니다. "스냅샷 다시 열기"는 두 파일로 트리를 다시 만드는 시간이고, 한
번 열면 그 안에서 사용자 증명은 건당 1초가 걸리지 않습니다. 최대 메모리는
한 프로세스에서 두 호출을 이어서 했을 때의 값입니다. 같은 원장을 계정·자산마다 한 줄(세로형)로 내보내면 파일이 훨씬 작고(자산 500종·계정 30만에서 163MB → 39MB) 걸리는 시간은 비슷합니다. 사용자
증명에는 경로상의 소계가 자산마다 들어가므로, 자산이 수백 종이면 한 건이
백 KB를 넘습니다. Node의 메모리 한도(`--max-old-space-size`)를 늘려 실행하면
그만큼 더 받습니다. 자산 500종에서 계정 30만을 넘는 규모는 추정일 뿐
실측하지 않았습니다.
