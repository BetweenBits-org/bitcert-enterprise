# 변경 내역과 상태

## 이 배포의 상태

살아 있는 답은 이 페이지가 아니라 `/v1/meta` 에서 읽으십시오 — 그쪽은 서비스가
생성하고, 이 페이지는 손으로 씁니다.

| | |
|---|---|
| 서비스 | `stonehash-attest-core` 0.1.0 |
| 환경 | `test` (샌드박스) |
| 앵커 백엔드 | **regtest** 위의 `bitcoind` |
| 번들 스키마 | `bitcert-proof-bundle/v1` |
| 무료 구간 | 사용 가능, 가입 불필요 |

**regtest가 뜻하는 것.** 증명의 수학적 검사 — 문서 일치, 묶음 포함,
트랜잭션 결합 — 는 여기서 mainnet과 똑같이 검증됩니다. 산술이고, 어느 체인인지는
무관하기 때문입니다. 체인 포함 여부는 이 배포에서 제3자가 확인할 수 없습니다. 블록을
저희가 채굴하기 때문입니다. 여기서 앵커링된 것은 파이프라인 전 구간을 그대로
재현하지만 공개적으로 검증 가능한 증명은 아닙니다.

mainnet으로 옮기면 앵커 백엔드만 바뀌고 그 외에는 아무것도 바뀌지 않습니다. 배치,
증명 생성, 검증은 손대지 않습니다 — 백엔드 이음매가 존재하는 이유가 그것입니다.

## 2026-11-19 — 국경간 송금 SDK: 판정은 축마다 비교합니다

**증빙 재검증이 파일에 적힌 축의 순서에 좌우되지 않습니다.**
`verifyEvidencePackage()`(TypeScript)와 `EvidenceVerifier.verify()`(Java)는
패키지에 적힌 판정과 직접 계산한 판정을 축마다 비교합니다. 커밋은 멤버를
정렬한 정규형에 대해 만들어지므로, 도구가 다시 써낸 패키지나 JSON 열에서
멤버 순서가 바뀌어 나온 패키지는 같은 패키지이고, 이제 같은 패키지로
읽힙니다. 차이가 있을 때 두 SDK는 같은 문장으로 알립니다.

- **한 곳은 더 엄격해졌습니다.** 한쪽에만 있는 축은 차이입니다. 패키지가
  이름만 적고 상태를 적지 않은 축도 이제 여기에 듭니다. 그런 패키지는 전에는
  판정 검사를 통과했고, 이제는 통과하지 못합니다.
- **Java SDK.** 증빙·정책·트래블룰 자료에서 글자나 숫자를 읽을 자리에
  `toString`이라는 멤버를 가진 객체가 있으면, 평가하지 않고 읽을 수 없는
  자료로 거절합니다(`unreadable_evidence`, `unreadable_policy`,
  `unreadable_compliance`). TypeScript SDK는 이런 입력에서 이미 멈췄습니다.
- **예제.** 두 SDK의 예제와 시험 자료에는 가상의 기관 이름만 씁니다.

플랫폼의 API는 그대로입니다. [SDK](#sdk)의 두 내려받기 묶음이 이 릴리스입니다.

## 2026-11-18 — 콘솔: 검증은 한 화면에서, 스냅샷은 앵커링 기록에서

**내려받은 증명을 확인하는 화면이 하나가 되었습니다.** 검증은 문서 앵커링
화면 아래에만 있었고, 준비금 증명 화면에는 확인 카드가 따로 있었습니다. 이제
메뉴의 **검증**이 어느 상품에서 받은 파일이든 확인합니다 — 앵커링 기록의
번들, 송금 증빙, 준비금 증명 파일. 파일이 무엇인지는 화면이 읽어서 알고,
검사는 모두 브라우저 안에서 이루어지며 서버로 보내는 것은 없습니다.

- **번들**: 해시가 번들에 실린 트랜잭션에 들어 있는지 확인합니다. 짝이 되는
  파일을 함께 넣으면 그 파일이 고정된 것인지까지 봅니다 — 문서는 문서의
  해시로, 준비금 증명 스냅샷은 준비금 증명 파일로, 송금 증빙은 그 증빙으로.
- **송금 증빙**: 파일 하나로 해시 일치, 증빙에 실린 기관 서명 공개키로 본
  서명, 판정 재계산, 앵커 번들을 확인합니다 — SDK의 `verifyEvidencePackage`와
  같은 네 검사입니다.
- **준비금 증명 파일**: 원본 잔고 파일과 함께 넣으면 루트·총액·계정 수를 다시
  계산해 맞춰 봅니다.

트랜잭션이 공개 블록에 있는지는 이 화면이 확인하지 않으며, 결과마다 그렇게
적습니다.

**준비금 증명 화면은 앵커링만 합니다.** 스냅샷은 앵커링 기록에 한 행으로
남고, 그 행의 "스냅샷 …"을 누르면 스냅샷 ID·머클 루트·계정 수·표본 확인
결과·앵커 상태가 보입니다. 송금 증빙의 기록에는 거래 ID가 붙어 해당 송금으로
이어집니다. 계정 증명 발급은 SDK(`openSnapshot`)에서 합니다. → [준비금 증명](#por)

## 2026-11-18 — 검증기: 함께 넣은 원본은 어느 번들에서든 대조합니다

**서명 앵커와 원본 전송의 번들에서도, 함께 넣은 파일이 앵커링된 문서인지
확인합니다.** 지금까지 `verifyBundle`은 문서의 해시를 앵커링한 번들에서만 원본을
대조했습니다. 서명 앵커의 번들은 서명문이 앵커링된 해시와 맞으면 문서
일치(`A`)를 통과로 보고했고, 원본 전송(콘솔의 원본 인스크립션)의 번들은 넣은
파일을 보지 않았습니다. 다른 파일을 넣어도 검증됨으로 나왔습니다. 고쳤습니다.

- **서명 앵커**: 넣은 파일의 해시가 서명문의 `document.sha256`과 다르면 `A`는
  `fail`이고 `verified`는 `false`입니다. 파일을 넣지 않으면 `A`는 `pass`가 아니라
  `skip`입니다. 서명문이 앵커링된 해시와 맞는지는 번들만으로 확인하고, 문서에
  대해서는 아무것도 말하지 않습니다 — 문서의 해시를 앵커링한 번들이 원본 없이
  답하는 방식과 같습니다.
- **원본 전송**: 넣은 파일이 트랜잭션에서 꺼낸 문서와 다르면 `A`는
  `fail`입니다(검사 `supplied-original`). 파일을 넣지 않았을 때의 답은
  그대로입니다.

검증 도구와 내려받는 `attest-verify` SDK에 반영했습니다. 이 패키지를 귀사
시스템에 넣어 쓰신다면 새로 내려받아 바꾸십시오. 서명 앵커의 번들을 원본 없이
검사하던 코드는 `links.A`가 `skip`으로 오는 것을 보게 됩니다. → [SDK](#sdk)

## 2026-11-18 — 국경간 송금: 전문 하나에 송금 하나, 플랫폼에서도

**같은 전문의 두 번째 접수를 플랫폼이 거절합니다.** 지급지시가 SWIFT 전문에서
만들어졌으면, 플랫폼은 접수할 때 그 전문에 이미 송금이 있는지 확인합니다 —
UETR이 같거나, 같은 파일의 같은 거래이거나, 한쪽에 UETR이 없을 때 식별자·
결제일·내용이 같은 다른 전문. 있으면 `409 duplicate_source_message`로, 그
UETR이 다른 지급에 쓰였으면 `409 reference_reused`로 거절하고, 응답의
`existing_payment_id`로 그 송금을 알려 줍니다. 두 요청이 같은 순간에 와도
송금은 하나입니다. 헤더 블록이 있는 MT103과 없는 같은 MT103이, 참조번호가
짧다는 이유로 두 번 지급되던 경우가 이로써 막혔습니다.

- `GET /v1/settlements`에 정확 일치 조회 `source_uetr`, `source_content`,
  `source_value_date`가 생겼습니다. SDK의 `submitSwift()`는 그 지급의 ID로 된
  송금과 그 UETR을 가진 송금을 조회하고, 다른 전문에 담긴 같은 지급이 어느
  송금인지는 플랫폼의 답을 따릅니다.
- 같아 보이는 두 지급은 여전히 두 지급입니다: 분할 지급 두 건이 든 파일을 다시
  출력하면 각 거래가 두 송금 가운데 하나씩에 맞춰지고, 둘 다 같은 송금에
  맞춰지지 않습니다.
- UETR도 지시번호·End-to-end ID도 없는 지급은 전문번호와 순번으로 알아봅니다 —
  같은 파일을 다시 출력해도 두 번 지급되지 않습니다.
- 직접 정한 `paymentId`는 이름일 뿐입니다. 이미 송금이 있는 전문으로 두 번째
  지급을 만들지 않습니다(이전에는 만들었습니다).
- 식별자와 내용이 같고 결제일이 없는 두 전문은 구분할 수 없으므로, 두 번째는
  지급하지 않고 거절합니다.
- UETR이 없는 지급에 SDK가 만드는 ID는 이제 `NOTPROVIDED`, `NONREF`, `NOREF`를
  End-to-end ID로 세지 않습니다. 이전 ID로 보낸 지급도 그대로 알아봅니다.
- `sourceMessage`의 `valueDate`는 `YYYY-MM-DD`로 쓴 달력상의 날짜여야 하며, 다른
  형식은 거절합니다(`400 invalid_source_message`).
- 전문 리더가 확신할 수 없는 것을 더 많이 거절합니다: 쉼표가 든 XML 금액,
  전문 두 건이 든 `Document`, 알 수 없는 수수료 부담 구분, 그 밖의 인코딩 선언,
  MT103의 빈 필드와 달력에 없는 결제일 등 — [국경간 송금](#corridor)의 「읽을 수
  있는 전문」에 목록이 있습니다.

## 2026-11-18 — 국경간 송금: Java SDK

**은행 시스템이 Java인 은행을 위한 SDK를 추가했습니다.** 외부 의존성이 없는 jar
하나이며 Java 11 이상에서 동작합니다(`attest-remit-java.tar.gz`). 전문을 그대로
넘기는 `submitSwift()`, 자체 데이터 지급, HSM·KMS 서명기, 트래블룰 모드 B,
Webhook 검증, 읽기 전용 클라이언트를 TypeScript SDK와 같은 규약으로 구현하고,
같은 기준 벡터로 맞춰져 있습니다. [국경간 송금](#corridor)의 예제는 이제
TypeScript와 Java 가운데 골라 볼 수 있습니다. 증빙 재검증
(`EvidenceVerifier.verify()`)은 TypeScript SDK와 같은 네 검사 — 논스 커밋, 요소
서명, 6축 판정, 비트코인 증명 파일 — 를 Java에서 다시 수행합니다.

## 2026-11-18 — 국경간 송금 가이드를 한 페이지로

**SDK를 귀행 시스템의 소스에서 호출하는 연동만 안내합니다.** SWIFT 전문 연동
페이지의 내용 — 읽을 수 있는 전문, 전문에서 지급지시로의 대응표, 같은 전문의
중복 판정, ISO 20022 상태코드와 `pacs.002` — 이 [국경간 송금](#corridor)으로
합쳐졌고, 이전 링크는 그 페이지로 열립니다. 터미널에서 실행하는 절차는
가이드에서 뺐고, 명령줄 도구와 폴더 어댑터는 내려받기 파일에서도 뺐습니다.
API 키, 서명 공개키 등록, 상품 활성화는 콘솔에서
합니다.

**서명키 없이 읽는 클라이언트.** 지급을 따라가기만 하는 시스템은
`readOnly: true`로 만든 클라이언트를 씁니다. 상태·상태 보고·증빙을 읽고,
서명하거나 보내는 호출은 거절합니다.

## 2026-11-18 — 준비금 증명: 보관할 파일은 하나, 표준 형식은 계정당 한 줄

**스냅샷이 남기는 것은 증명 파일 하나입니다 — 콘솔에서도, SDK에서도.**
이전에는 스냅샷마다 다섯 파일(선언문, 계정별 리프, 시드, 트리 머리말,
제출본)을 한 폴더에 보관해야 했습니다. 이제 보관할 것은 앵커링에 쓴 잔고
파일과 증명 파일, 두 가지입니다. 증명 파일에는 선언문·서명·시드와 잔고
파일을 읽은 방식이 들어 있고, 계정이나 잔고는 들어 있지 않습니다. 콘솔과
SDK의 증명 파일은 같은 형식이라, 콘솔에서 받은 파일은 SDK가 그대로 열고 SDK가
만든 파일은 콘솔의 검증 화면이 확인합니다.

**SDK는 호출 두 번입니다.** `anchorBalanceFile`이 잔고 파일을 검사하고
트리를 만들어 서명·제출한 뒤 증명 파일을 남깁니다 — 증명 파일은 제출 전에
먼저 쓰이고, 응답을 받지 못했다면 같은 호출을 다시 해 끝냅니다.
`openSnapshot`은 두 파일로 스냅샷을 다시 열어 사용자 증명을 발급하며, 잔고
파일이 원본과 다르면 무엇이 달랐는지 알려 주고 아무것도 발급하지 않습니다.
콘솔은 검증 화면에서 두 파일로 같은 확인을 하고, 사용자 증명 발급은 SDK가
합니다. 이전 버전의 SDK가 남긴 폴더는 계속 읽습니다. → [준비금 증명](#por)

**가이드는 귀사 시스템의 소스에서 SDK를 호출하는 연동만 안내합니다.**
터미널에서 실행하는 절차와 키 등록 스크립트, 퀵스타트 실행 안내를 뺐습니다.
API 키, 서명 공개키 등록, 상품 활성화는 콘솔에서 합니다.

**잔고 파일의 표준 형식은 계정당 한 줄입니다.** 첫 열이 `account_id`,
나머지 열이 자산인 CSV를 표준으로 안내하고, 콘솔의 예시 파일과 가이드의
내보내기 쿼리도 이 형태로 바꿨습니다. 계정·자산마다 한 줄인 CSV, 잔고·부채
열 CSV, JSON은 이전과 같이 읽으며, 어느 형태로 내보내도 같은 루트가
나옵니다. → [잔고 파일 준비](#por-data)

## 2026-11-17 — SWIFT 전문으로 보내고, ISO 20022 상태로 받기

**지급 시스템이 이미 만드는 전문을 그대로 보냅니다.** 은행 SDK가 MT103,
pacs.008, pain.001을 있는 그대로 읽어 서명된 지급지시로 바꾸고, 결과를
`pacs.002` 상태 보고로 돌려줍니다. 전문의 참조번호 — UETR, 지시번호,
End-to-end ID — 가 전문 파일의 SHA-256과 함께 지급지시에 서명되어 실리며,
콘솔의 송금 검색이 이 번호로 지급을 찾습니다. 같은 전문을 두 번 넘겨도 지급은
하나입니다. [국경간 송금](#corridor)을 보십시오.

**HSM으로 서명.** `RemitClient`가 `key` 대신 `signer`를 받으며, 서명은 쓰이기
전에 등록된 공개키로 검증됩니다. 트래블룰 모드 B — 당사자 정보를 은행 쪽에서
암호화 — 가 SDK에 `travelRule: 'B'`로 들어갔습니다. 은행의 심사 결과는 이제
고정값이 아니라 입력(`review`)이고, `verifyWebhook()`이 Webhook 전달을
검증합니다.

**가이드와 레퍼런스.** [국경간 송금](#corridor)이 Webhook, 연동 중 만나는 오류,
일별 대사, 샌드박스 시험 레버를 다루고, API 레퍼런스에는 송금 엔드포인트의
요청 본문이 들어갔습니다.

**추측하지 않고 거절합니다.** 지급이 여러 건 든 파일은 모든 건을 읽습니다.
다른 종류의 전문 — MT102, MT103의 커버 전문 — 은 MT103으로 읽지 않고
거절합니다. 같은 참조번호가 다른 지급에 다시 쓰이면 반복으로 보지 않고
`reference_reused`로 알립니다. 다른 경로의 지급, 개인으로 식별된 당사자,
시험 전문으로 표시된 전문은 보내지 않습니다. 보내는 금액은 수수료를 누가
부담하든 수취인이 받아야 할 금액입니다.

*SDK 0.2.0. 프로세스 안의 키를 쓰는 `buildInstruction()`은 그대로이며,
`buildInstructionAsync()`가 서명기에도 쓸 수 있는 형태입니다.*

## 2026-11-17 — 준비금 증명: 잔고 파일 네 형태, 자산이 수백 종인 거래소

**잔고 파일을 네 형태로 받습니다.** 세로형·가로형 CSV에 더해, 자산마다
잔고 열(`e_`)과 부채 열(`d_`)을 둔 시트형 CSV와 계정 배열
JSON(`--accounts-json`)을 읽습니다. 같은 원장은 어느 형태로 내보내도 같은
루트가 나옵니다. 부채가 0이 아닌 계정이 있으면 빼지도 무시하지도 않고
파일을 거부하며(`debt_not_supported`), JSON의 금액은 문자열이어야 합니다.
자산이 많은 거래소는 자산 목록을 파일로 줍니다(`--assets-file`).
[잔고 파일 준비](#por-data)를 보십시오.

**트리는 보유한 잔고만 적습니다.** 새 트리 형식 `merkle-sum-sha256-v2`는
0인 잔고와 아무도 보유하지 않은 자산을 적지 않습니다. 해시 식은
그대로입니다. 상장 자산이 500종이어도 필요한 메모리와 시간은 계정이
실제로 가진 잔고의 수를 따릅니다 — 계정 30만 개, 자산 500종, 계정당
5종 보유에서 빌드 31초, 최대 메모리 1.9GB입니다. 보유한 계정이 없는
자산은 목록에 넣든 빼든 루트가 같습니다.

**기존 호출 측에서 달라지는 점.** SDK가 새로 만드는 스냅샷은 v2이며,
선언문의 `tree.algo`가 형식을 밝힙니다. 같은 원장이라도 v1과 v2의 루트는
다릅니다. 플랫폼은 두 형식을 모두 접수하고 검증합니다 — 이전에 만든
스냅샷과 디렉터리, 이미 발급한 증명은 그대로 유효하고, 검증기와 공개
검증 페이지는 두 형식의 증명을 같은 방식으로 확인합니다. 이전 형식으로
만들어야 한다면 `build --tree-format v1`입니다.

**콘솔에서 바로.** 콘솔의 준비금 증명 화면에서 잔고 파일을 고르면
브라우저가 SDK와 같은 코드로 루트를 만들고, 서명된 선언문만 제출합니다 —
파일은 올라가지 않습니다. 네 형태를 모두 받으며, 각 형태의 예시 파일을
그 화면에서 내려받을 수 있습니다.

## 2026-11-16 — 귀사 잔고 파일로 만드는 준비금 증명

**잔고 파일은 귀사 서버에서 읽습니다.** 거래소 SDK가 귀사 원장의 CSV
내보내기를 직접 읽습니다 — 계정·자산마다 한 줄, 또는 계정마다 한 줄 —
검사하고, 거기서 루트를 만듭니다. 금액 변환은 정확하거나 거부되며, 문제가
하나라도 있는 파일로는 아무것도 만들지 않습니다. 새 명령은 `check`,
`sign`, `submit`, `status`이고 `build`가 `--csv`를 받습니다.
[잔고 파일 준비](#por-data)를 보십시오.

**스냅샷은 서명만으로 앵커됩니다.** `POST /v1/por/snapshots`가 서명된
선언문을 받아, 어떤 계정도 열어 보라고 요구하지 않고 앵커링합니다. 표본
확인은 요청할 때 그대로 쓸 수 있습니다(`"spot_check": true`, 또는
`submit --spot-check`). 모든 스냅샷의 공개 자료가 어느 경로였는지
말하며(`spot_check`, `platform_checks`), 표본을 보지 않은 스냅샷을 표본을
본 것처럼 말하지 않습니다.

**기존 호출 측에서 달라지는 점.** `spot_check` 없이 보낸 요청은 전에는
챌린지로 응답받았지만, 이제는 상태 `ACCEPTED`로 바로 접수됩니다. 이전
동작을 유지하려면 `"spot_check": true`를 보내십시오.
`PorClient.publish`도 같은 기본값을 따릅니다. SDK의 비공개 파일도
바뀌었습니다: 트리를 통째로 저장하지 않고 `leaves.jsonl`에서 다시 만들며,
이 덕분에 계정 100만 개를 받을 수 있습니다. 이전 버전이 쓴 디렉터리도
그대로 읽습니다.

## 2026-11-13 — 귀사 기록의 보존 기한 폐지

귀사 조직이 API 키나 콘솔로 만든 기록에는 보존 기한이 없습니다. 삭제를 요청하실
때까지 보관되며, 샌드박스와 상용이 같은 규칙을 따릅니다. 가입 없이 쓰는 무료 구간
기록만 `/v1/meta` 가 알려 주는 기간이 지나면 사라집니다.

- 콘솔의 30일 보존 표시를 없앴고, 이전에 콘솔에서 만든 기록에 붙어 있던 만료일도
  지웠습니다.
- `/v1/console/me` 와 `/v1/meta` 의 `console` 블록에서 `retention_days` 를
  뺐습니다. `free_tier.retention_days` 는 그대로입니다.
- 귀사 기록은 만료되지 않으므로, 콘솔 대시보드는 더 이상 `attest.expiring_7d` 와
  `expiring` 주의 항목을 보고하지 않습니다.

## 2026-11-12 — 운영 콘솔, 송금 추적, 이 허브

**콘솔 대시보드.** 구독·빌링이 먼저 — 이번 달 비용, 플랜, 청구 기간을 상품별로 —
그다음 구독한 상품마다 한 줄, 왼쪽에는 오늘의 숫자, 오른쪽에는 최근 몇 건.

**송금.** 거래 한 건을 구간별로 펼쳐 봅니다 — 접수·은행 승인, 트래블룰, USDC 정산,
현지 지급, 입금 확정·증빙 앵커 — 서명된 이벤트에서 읽어 내고, 그 아래에 서명 이벤트
로그가 있습니다. 원장에는 거래마다 체인 거래가 보이고, USDC 정산 구간은
`GET /v1/settlements/{id}/chain` 으로 정산 체인 노드에 직접 묻습니다 — 블록, 확인 수,
성공 여부. 현지 지급 구간은 지급을 확인한 기관과 그 영수증의 서명 여부를 밝힙니다.
검색창은 거래 ID, USDC 거래해시, 은행 참조번호를 받고, 원장은 거래일로 거르고 CSV로
내보냅니다.

**신뢰.** 연동 화면이 이 조직에 대해 플랫폼이 신뢰하는 기관과 서명 공개키를 보여
줍니다 — 귀사의 키 저장소와 대조할 공개키 해시(SHA-256)와 함께. 은행·거래소가 보유한
공개키를 그 자리에서 등록하고, 기관의 서명 검증 키로 적용하며
(`POST /v1/console/institutions/{id}/signing-key`), 폐기합니다.

**감사 기록.** 콘솔 화면과 `GET /v1/console/audit` 이 귀사의 API 키와 콘솔 계정으로
인증된 모든 호출을 보여 줍니다 — 누가, 언제, 어느 서비스에서, 어떤 결과로 — 로그인
포함.

**이 허브.** 그룹으로 묶인 메뉴, 첫 페이지가 된 [개요](#overview), 선택한 언어를
따르는 공통 화면 요소.

## 2026-11-11 — 송금과 준비금 증명

**국경간 송금.** 은행 어댑터 SDK(`attest-remit`), 서명 이벤트를 담은
`/v1/settlements` 원장, 증빙 패키지, 일별 마감 대사, 웹훅.

**준비금 증명.** 거래소 SDK(`attest-por`), 스팟체크와 앵커링이 붙은

**콘솔.** 상품별 구독 — 기관 등록과 브라우저에서 생성하는 서명키 포함. 서명키는 귀사
서버에서 `POST /v1/issuer-keys` 로도 등록할 수 있습니다. API 키는 여러 개를 동시에
두고(2026-11-06부터) 각각 발급·라벨·폐기합니다.

**저장소.** SQLite와 나란히 MySQL을 하나의 저장 모듈로 지원 — 두 번째 코드 경로
없이 운영용 엔진을 씁니다.

## 0.1.0 — 2026-11-05

처음 공개하는 표면.

**서비스.** 단일 프로세스: 발급, 배치, Merkle 집계, 앵커링, 내보내기를 SQLite
하나 위에서 처리합니다. 배처는 API 프로세스 안의 타이머입니다 — 브로커도,
게이트웨이도, 서비스별 배포 단위도 없습니다. 런타임 의존성 0: `node:sqlite`,
`node:http`, `node:crypto`, 그리고 TypeScript는 Node가 직접 벗겨 냅니다. 따라서
배포는 "트리를 복사하고, 환경변수를 넣고, node를 실행"입니다.

**API.** 서빙되는 모든 라우트가 문서화되어 있습니다 — 그룹과 개수는
[API 레퍼런스](#api) 그대로이며, 빠짐이 없는지 테스트가 서버의 라우트 표와 대조합니다. 생존·준비
확인, `/v1/meta`, 증명 내보내기를 포함한 키 기반 증명 수명주기, 인증 없는 무료
구간, 상태를 두지 않는 정산 대조와 아카이브 조립, 셀프서브 샌드박스 키.

**무료 구간.** 계정도 키도 없이 해시를 앵커링합니다. 주소당·서비스 전체로 상한이
있고, 무료 앵커는 자기 트랜잭션을 만들지 않고 평범한 공유 배치에 들어갑니다. 기록은
보존 기간이 지나면 사라지지만, 내려받은 증명 파일은 그렇지 않습니다.

**검증기.** `@stonehash/attest-verify` 를 소스로 공개 — 이 허브의 체크섬 달린
tarball로, 아직 npm에는 없습니다. 의존성 0, Node와 브라우저에서 동일, 와이어 계약의
의도적으로 독립적인 두 번째 구현. 적합성 픽스처 여덟 개: 반드시 검증되는 다섯 개와
반드시 실패하는 변조된 세 개.

**증빙 규격.** `bitcert-proof-bundle/v1` 전문 공개. 제3자가 저희에게 아무것도 묻지
않고 자기 검증기를 구현할 수 있도록.

**정산 규칙 엔진.** 판정 축 여섯 개, 항상 따로 보고. 정책은 코드가 아니라
데이터입니다. `dataMode: "SYNTHETIC"` 과 `regulatoryDecision: "NOT_EVALUATED"` 는
산문으로 약속하는 대신 테스트로 강제합니다.

**플레이그라운드.** 앵커링 패널과 탐색을 포함한 검증 패널 — 모두 브라우저 안에서만
돌며 번들러도 프레임워크도 없습니다. 문서는 업로드되지 않고, 증명 파일의 검증은
StoneHash 엔드포인트에 접속하지 않습니다.

**이 개발자 허브.** 빠른 시작, OpenAPI 3.1 레퍼런스, 증빙 규격, 공개 테스트 벡터,
SDK 표면, 그리고 이 페이지. 서버가 등록한 라우트가 레퍼런스에 빠지거나 그 반대이면
테스트가 실패하므로, 설명하는 API와 소리 없이 어긋날 수 없습니다.

## 일부러 만들지 않은 것

빠진 것이 아니라 결정임을 알 수 있도록 적어 둡니다.

- 메시지 버스, API 게이트웨이, Helm 차트, 서비스 메시 없음. 표면 전체가
  [API 레퍼런스](#api)의 라우트 표이고, 프로세스 하나가 서빙합니다.
- OP_RETURN v30 인코더 없음 — 특허 출원 중이고, `BC01` 이 증명에 필요한 모든 것을
  담습니다.
- mainnet 핫월렛 없음. `bitcoind` 가 지갑을 쥐고 앵커 트랜잭션에 서명하므로, 어느
  네트워크에서도 지갑 키가 서비스 프로세스에 들어오지 않습니다.
- OpenTimestamps 없음. 앵커링은 자체 파이프라인으로 돕니다.
- 공인 CA·TSA 연동 없음, 신원 확인 없음. 서명 유효성과 발행 기관 신원은 별개의
  줄로 남습니다.
- 증명 경로에 자체 탐색기 없음. 샌드박스 콘솔은 편의상 저희가 호스팅하는 탐색기로
  링크하지만, 체인 포함 여부는 귀사가 고른 조회처를 통해 귀사가 확인할 몫입니다 —
  그것이 요점입니다.
