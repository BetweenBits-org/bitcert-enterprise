# Changelog & Status

## Status of this deployment

Read `/v1/meta` for the live answer rather than trusting this page — it is
generated by the service, and this page is written by hand.

| | |
|---|---|
| Service | `stonehash-attest-core` 0.1.0 |
| Environment | `test` (sandbox) |
| Anchor backend | `bitcoind` on **regtest** |
| Bundle schema | `bitcert-proof-bundle/v1` |
| Free tier | enabled, no signup |

**What regtest means for you.** The proof's arithmetic checks — document match,
batch inclusion, transaction binding — verify here exactly as they would on
mainnet; they are arithmetic, and the chain is irrelevant to them. Chain
inclusion cannot be confirmed by a third party on this deployment, because we
mine the blocks. Anything anchored here is a faithful exercise of the whole
pipeline and not a publicly verifiable proof.

Moving to mainnet changes the anchor backend and nothing else. Batching, proof
assembly and verification are untouched — that is what the backend seam is for.

## 2026-11-19 — Cross-border Settlement SDKs: the verdict is compared axis by axis

**Evidence re-verification no longer depends on the order a file lists its
axes in.** `verifyEvidencePackage()` (TypeScript) and
`EvidenceVerifier.verify()` (Java) compare the verdict a package states with
the one they compute, axis by axis. The commitment is made over a canonical
form that sorts members, so a package that a tool wrote out again, or that a
JSON column returned with its members in another order, is the same package —
and now reads as the same package. Both SDKs report a difference in the same
words.

- **Stricter in one place.** An axis only one side has is a difference, and
  that now includes an axis the package names without giving it a state. Such
  a package used to pass the verdict check; it fails it now.
- **Java SDK.** Evidence, a policy or Travel Rule data in which an object with
  a member named `toString` stands where text or a number is read is refused
  as unreadable (`unreadable_evidence`, `unreadable_policy`,
  `unreadable_compliance`) instead of being evaluated. The TypeScript SDK
  already stopped on such input.
- **Samples.** The examples and test data of both SDKs name made-up
  institutions only.

The API of the platform is unchanged. Both downloads on [SDKs](#sdk) carry
this release.

## 2026-11-18 — Console: one screen to verify on, and snapshots in Records

**There is one screen for checking a downloaded proof.** The check used to sit
at the foot of Document anchoring, and Proof of Reserves had a card of its own
for it. **Verify**, in the menu, now checks a file from any product — a bundle
from Records, a settlement's evidence, a reserve proof file. The screen reads
what the file is; every check runs in the browser and nothing is sent to a
server.

- **A bundle**: the hash is checked to be inside the transaction the bundle
  carries. Add the file that goes with it and that file is checked against
  what was anchored — a document by its hash, a reserve snapshot by its
  reserve proof file, a settlement's evidence by that evidence.
- **Settlement evidence**: one file — the hash, the signatures under the
  institutions' signing public keys the evidence carries, the verdict
  recomputed and the anchor bundle, the same four checks as the SDK's
  `verifyEvidencePackage`.
- **A reserve proof file**: added with the original balance file, the root,
  the totals and the account count are rebuilt and compared.

Whether the transaction is in a public block is not checked by this screen,
and every result says so.

**The Proof of Reserves screen anchors and does nothing else.** A snapshot is
a row in Records, and pressing "snapshot …" on the row shows its snapshot id,
Merkle root, account count, spot-check result and anchor status. A
settlement's evidence record carries its payment id and leads to that
settlement. Issuing an account's proof is done with the SDK (`openSnapshot`).
→ [Proof of Reserves](#por)

## 2026-11-18 — Verifier: a file you supply is checked against every kind of bundle

**The file you supply is now checked against what was anchored for signed
anchors and for inscribed documents too.** Until now `verifyBundle` held the
original only against bundles that anchor a document's hash. For a signed
anchor it reported `A` (document match) as passed once the signed statement
matched the anchored hash, and for an inscribed document it did not look at
the supplied file. A different file still came out as verified. That is fixed.

- **Signed anchors**: when the supplied file does not hash to the
  `document.sha256` of the signed statement, `A` is `fail` and `verified` is
  `false`. Without a file, `A` is `skip`, not `pass`. The statement is checked
  against the anchored hash from the bundle alone, and nothing is said about
  the document — the way a bundle of a document's hash has always answered
  without its original.
- **Inscribed documents**: when the supplied file is not the document
  recovered from the transaction, `A` is `fail` (check `supplied-original`).
  The answer without a file is unchanged.

The verification tool and the `attest-verify` download carry the fix. If you
have this package in a system of your own, download it again and replace it.
Code that checks a signed anchor's bundle without the original will see
`links.A` arrive as `skip`. → [SDKs](#sdk)

## 2026-11-18 — Cross-border Settlement: one message, one settlement — on the platform too

**The platform refuses a second settlement for the same message.** Where an
instruction was made from a SWIFT message, the platform checks at acceptance
whether that message already has a settlement — the same UETR, the same
transaction of the same file, or, where one of the two has no UETR, another
message with the same identifiers, value date and content. If it has, the
instruction is refused with `409 duplicate_source_message`, or with
`409 reference_reused` when its UETR stands on a different payment, and the
answer names that settlement in `existing_payment_id`. Two requests arriving
at the same moment still make one settlement. This closes the case in which
an MT103 with and without its header blocks was paid twice because its
reference was short.

- `GET /v1/settlements` has exact lookups: `source_uetr`, `source_content`
  and `source_value_date`. The SDK's `submitSwift()` looks up the settlement
  under the payment's id and the one that holds its UETR; which settlement
  another rendering of a payment belongs to is the platform's answer.
- Two payments that read alike are still two: a file with two instalments
  written out again has each transaction matched to one of the two
  settlements, never both to the same one.
- A payment with neither a UETR nor an instruction or end-to-end id is
  recognised by its message id and position — the same file exported again
  is no longer paid twice.
- A `paymentId` of your own is a name and nothing more. It does not make a
  second payment out of a message that already has a settlement (it used to).
- Two messages with the same identifiers and content and no value date
  cannot be told apart: the second is refused, not paid.
- The id the SDK derives for a payment without a UETR no longer counts
  `NOTPROVIDED`, `NONREF` or `NOREF` as an end-to-end id. A payment sent
  earlier under the older id is still recognised.
- `valueDate` in `sourceMessage` must be a calendar day written `YYYY-MM-DD`;
  any other form is refused (`400 invalid_source_message`).
- The message readers refuse more of what they cannot be sure of: an XML
  amount with a comma, a `Document` holding two messages, an unknown charge
  bearer, other declared encodings, an empty field or an impossible value
  date in an MT103 — the list is under "Messages that are read" in
  [Cross-border Settlement](#corridor).

## 2026-11-18 — Cross-border Settlement: a Java SDK

**An SDK for banks whose systems are Java.** One jar with no third-party
dependency, for Java 11 or later (`attest-remit-java.tar.gz`). It implements
`submitSwift()` for a message as your system wrote it, payments from your own
data, a signer over an HSM or KMS, Travel Rule mode B, webhook verification
and a read-only client under the same conventions as the TypeScript SDK, and
is held to the same reference vectors. The examples in
[Cross-border Settlement](#corridor) can now be read in TypeScript or in Java.
Evidence re-verification (`EvidenceVerifier.verify()`) runs the same four
checks as the TypeScript SDK — nonce commitment, element signatures, six-axis
verdict, Bitcoin proof file — in Java.

## 2026-11-18 — One guide for Cross-border Settlement

**The guide covers one way to integrate: your system's source calls the
SDK.** What the SWIFT Messages page held — the messages that are read, the
table from message to instruction, how a repeated message is recognised, the
ISO 20022 status codes and the `pacs.002` — is now part of
[Cross-border Settlement](#corridor), and old links open there. Steps run
from a terminal are no longer part of the guide, and the command line and
the folder adapter are no longer part of the download. API keys, registering a
signing public key and activating the product are done in the console.

**A client that reads without a signing key.** A system that only follows
payments uses a client made with `readOnly: true`: it reads the status, the
status report and the evidence, and refuses whatever would sign or send.

## 2026-11-18 — Proof of Reserves: one file to keep, and one row per account as the standard

**A snapshot leaves one proof file — from the console and from the SDK
alike.** It used to leave five per snapshot (the statement, a leaf per
account, the seed, a tree header, the submission) to be kept together in a
folder. What is kept now is the balance file that was anchored and the proof
file — two files. The proof file carries the statement, its signature, the
seed and how the balance file was read; it holds no account and no balance.
The console's and the SDK's proof files are the same format: the SDK opens
one the console handed back, and the console's Verify screen checks one the
SDK wrote.

**The SDK is two calls.** `anchorBalanceFile` checks the balance file, builds
the tree, signs, submits and leaves the proof file — written before the
statement is sent, so if the answer never arrives the same call made again
finishes the job. `openSnapshot` opens the snapshot again from the two files
and issues customers' proofs; a balance file that is not the original is
refused, with what differed, and nothing is issued. The console does the same
check from the two files on its Verify screen; issuing customers' proofs is
the SDK's. A directory left by an earlier version of the SDK is still read.
→ [Proof of Reserves](#por)

**The guide covers one way to integrate: your system's source calls the
SDK.** Steps run from a terminal, the key-registration script and the
quick-start run are no longer part of it. API keys, registering a signing
public key and activating the product are done in the console.

**The standard balance file is one row per account.** The guide now leads
with a CSV whose first column is `account_id` and whose other columns are
assets, and the console's example file and the guide's export queries are in
that shape. A CSV with one row per account and asset, a CSV with balance and
debt columns, and JSON are read as before, and one ledger gives the same root
whichever shape it is exported in. → [Preparing the Balance File](#por-data)

## 2026-11-17 — SWIFT messages in, ISO 20022 status out

**Send the message your payment system already writes.** The bank SDK
reads an MT103, a pacs.008 or a pain.001 as it is, turns it into a signed
settlement instruction, and reports the outcome as a `pacs.002` status
report. The message's own references — UETR, instruction id, end-to-end id —
are signed into the instruction with the SHA-256 of the message file, and the
console's settlement search finds a payment by them. The same message handed
over twice is one payment. See [Cross-border Settlement](#corridor).

**Sign with an HSM.** `RemitClient` takes a `signer` in place of a `key`; a
signature is verified against the registered public key before it is used.
Travel Rule mode B — the party data encrypted on the bank's side — is in the
SDK as `travelRule: 'B'`. The bank's own review results are now inputs
(`review`) instead of fixed values, and `verifyWebhook()` checks a delivery.

**The guide and the reference.** [Cross-border Settlement](#corridor)
documents webhooks, the errors an integration meets, the daily manifest and
the sandbox test levers, and the API Reference carries the request bodies of
the settlement endpoints.

**It refuses rather than guesses.** A file with several payments yields
every one of them; a message of another type — an MT102, the cover of an
MT103 — is refused instead of being read as an MT103; a reference that
comes back on a different payment is reported as `reference_reused` instead
of being taken for a repeat; and a payment of another route, a party
identified as a private person or a message marked as a test is not sent.
The amount sent is what the beneficiary is owed, whichever way the charges
fall.

*SDK 0.2.0. `buildInstruction()` is unchanged for a key held in the process;
`buildInstructionAsync()` is the form that also works with a signer.*

## 2026-11-17 — Proof of Reserves: four file shapes, and exchanges that list hundreds of assets

**A balance file is read in four shapes.** Beside the long and wide CSV, the
SDK reads a sheet CSV — a balance column (`e_`) and a debt column (`d_`) per
asset — and a JSON array of accounts (`--accounts-json`). One ledger gives
the same root whichever shape it is exported in. An account whose debt is not
zero is neither netted nor passed over: the file is refused
(`debt_not_supported`). An amount in JSON must be a string. An exchange with
many assets gives its asset list as a file (`--assets-file`). See
[Preparing the balance file](#por-data).

**The tree writes only what is held.** The new tree format,
`merkle-sum-sha256-v2`, leaves out a zero balance and an asset nobody holds.
The hash formulas are unchanged. With 500 assets listed, memory and time
follow the number of balances accounts actually hold — 300,000 accounts over
500 assets, five held each, build in 31 seconds at a peak of 1.9 GB. An asset
that no account holds can be listed or not, and the root is the same.

**What changes for existing callers.** Snapshots the SDK builds from now on
are v2, and `tree.algo` in the statement says so. The v1 and v2 roots of one
ledger differ. The platform accepts and verifies both — snapshots and
directories made earlier, and proofs already issued, stay valid, and the
verifier and the public verify page check a proof of either format the same
way. To build the earlier format: `build --tree-format v1`.

**Straight from the console.** Choose a balance file in the console's Proof
of Reserves screen and the browser builds the root with the same code as the
SDK and submits the signed statement, nothing else — the file is not
uploaded. All four shapes are read, and an example of each can be downloaded
from that screen.

## 2026-11-16 — Proof of Reserves from your own balance file

**The balance file is read on your server.** The exchange SDK now reads a CSV
export of your ledger directly — one row per account and asset, or one row per
account — checks it, and builds the root from it. Amounts are converted
exactly or refused; a file with any problem builds nothing. The new commands
are `check`, `sign`, `submit` and `status`, and `build` takes `--csv`. See
[Preparing the Balance File](#por-data).

**A snapshot is anchored on its signature.** `POST /v1/por/snapshots` now
accepts a signed statement and anchors it without asking for any account to
be opened. The spot check is still there when you ask for it
(`"spot_check": true`, or `submit --spot-check`). Every snapshot's public
material says which path it took (`spot_check`, `platform_checks`), and a
snapshot that was not sampled is never described as sampled.

**Changed for existing callers.** A request without `spot_check` used to be
answered with a challenge; it is now accepted at once with status `ACCEPTED`.
Send `"spot_check": true` to keep the earlier behaviour. `PorClient.publish`
follows the same default. The SDK's private files changed too: the tree is
rebuilt from `leaves.jsonl` instead of being stored whole, which is what lets
a million accounts through; directories written by the earlier version are
still read.

## 2026-11-13 — Your records no longer expire

Records your organisation makes — with an API key or in the console — have no
retention period: they are kept until you ask for them to be deleted, and the
sandbox and production follow the same rule. Only free-tier records, which need
no signup, still expire after the window `/v1/meta` reports.

- The console no longer shows a 30-day retention, and the expiry that earlier
  console records carried has been cleared.
- `retention_days` is gone from `/v1/console/me` and from the `console` block of
  `/v1/meta`; `free_tier.retention_days` stays.
- The console dashboard no longer reports `attest.expiring_7d` or `expiring`
  attention items: nothing of yours can expire.

## 2026-11-12 — Operations console, settlement tracking, this hub

**Console dashboard.** Subscription and billing first — this month's charges so
far, the plan and the billing period, line by line — then one full-width row per
subscribed product, the day's numbers on the left and the last few events on the
right.

**Settlements.** A settlement opens leg by leg — accepted and bank-authorised,
travel rule, USDC settlement, local payout, credit confirmed and anchored —
read from its signed events, with the signed event log beneath. The ledger shows
each settlement's chain transaction, and the USDC leg asks the settlement
chain's node directly — block, confirmations, success — through
`GET /v1/settlements/{id}/chain`. The payout leg names the institution that
confirmed it and whether its receipt is signed. The search box takes a payment
id, a USDC transaction hash or the bank's own reference; the ledger filters by
transaction date and exports as CSV.

**Trust.** The Integrate screen lists the institutions and the signing public
keys the platform trusts for your organisation, each with its SHA-256 hash to
compare against your own key store. A bank's or exchange's own public key is
registered there, applied as an institution's verification key
(`POST /v1/console/institutions/{id}/signing-key`), and revoked in place.

**Audit log.** A console screen and `GET /v1/console/audit` list every
authenticated call made with your API keys and console accounts — who, when,
which service, and the result — sign-ins included.

**This hub.** Grouped navigation, the [Overview](#overview) as the landing page,
and page chrome that follows the selected language.

## 0.1.0 — 2026-11-05

First published surface.

**Service.** Single process: issue, batch, Merkle-aggregate, anchor and export,
over one SQLite database. The batcher is a timer inside the API process — no
broker, no gateway, no per-service deployment unit. Zero runtime dependencies:
`node:sqlite`, `node:http`, `node:crypto`, and Node strips the TypeScript
itself, so deployment is "copy the tree, set the environment, run node".

**API.** Every served route is documented — see the [API Reference](#api),
whose coverage a test checks against the server's route table. Liveness and
readiness; `/v1/meta`; the keyed attestation lifecycle with
proof export; the unauthenticated free tier; stateless settlement
reconciliation and archive assembly; self-serve sandbox keys.

**Free tier.** Anchor a digest with no account and no key. Capped per address
and service-wide; free anchors join the ordinary shared batch rather than
triggering their own transaction; records expire after the retention window,
while the downloaded proof file does not.

**Verifier.** `@stonehash/attest-verify` published as source, in the
checksummed tarballs on this hub (not on npm yet) — zero dependencies,
identical in Node and the browser, a deliberately independent second
implementation of the wire contract. Eight conformance fixtures: five that must
verify and three tampered ones that must fail.

**Evidence specification.** `bitcert-proof-bundle/v1` published in full, so a
third party can implement their own verifier without asking us anything.

**Settlement rules engine.** Six judgement axes, always reported separately.
Policies are data, not code. `dataMode: "SYNTHETIC"` and
`regulatoryDecision: "NOT_EVALUATED"` are enforced by test rather than promised
in prose.

**Playground.** An Anchor panel and a Verify panel with Explore — running
entirely in the browser with no bundler and no framework. No document is
uploaded, and verifying a proof file contacts no StoneHash endpoint.

**This Developer Hub.** Quick Start, the OpenAPI 3.1 reference, the evidence
specification, the public test vectors, the SDK surface, and this page. A test
fails whenever a route the server registers is missing from the reference, or
the reverse, so it cannot quietly drift from the API it describes.

## Not built, deliberately

Listed so the absences read as decisions rather than gaps.

- No message bus, API gateway, Helm chart or service mesh. The whole surface is
  the route table in the [API Reference](#api), served by one process.
- No OP_RETURN v30 encoder — patent-pending, and `BC01` carries everything a
  proof needs.
- No mainnet hot wallet. `bitcoind` holds the wallet and signs anchor
  transactions, so no wallet key enters the service process on any network.
- No OpenTimestamps. Anchoring runs on our own pipeline.
- No accredited CA or TSA integration, and no identity verification. Signature
  validity and issuer identity stay separate rows.
- No explorer of our own in the proof path. The sandbox console links to one we
  host for convenience, but chain inclusion is yours to establish through a
  source you choose — which is the point.
